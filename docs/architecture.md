# Architecture

A pnpm workspace with three applications that ship together: the mobile app and the API it talks
to share one contract, which the API generates and the repository commits; the landing is the
public site, served with the app's links in front of the API.

```
apps/
  mobile/         Expo app (React Native, Expo Router), typed client from the contract
  api/            NestJS HTTP API, Prisma (PostgreSQL), Zod, served under /api
  landing/        public site (Astro, static, English and Spanish) and the web image (nginx)
openapi/          openapi.json: the committed API contract, generated by the API
observability/    the API's metric catalog, Grafana dashboards, Prometheus SLOs and alert rules (tested)
deploy/vps/       the reference deployment of the server side: Caddy, the web image, the API, PostgreSQL, Redis
infra/terraform/  the same server on DigitalOcean, as code (optional)
.zap/             the rules of the dynamic analysis (OWASP ZAP)
scripts/          repository tooling (hooks, gates, `pnpm dev`, pinned tool images, deployment checks)
e2e/              browser suite (Playwright): the landing, and the web image's app links
docs/             standards, guides, ADRs
.github/          CI/CD workflows, templates, CODEOWNERS, Dependabot, rulesets
docker-compose.yml  development services, the production-like stack, a local telemetry backend
```

Each app owns its `package.json`, `tsconfig`, tests and build: the API is shipped as a container
image (`apps/api/Dockerfile`), the landing as the `web` image (`apps/landing/Dockerfile`), the app
as store builds and OTA updates through EAS. Tooling that must behave the same everywhere (ESLint,
Prettier, commitlint, hooks) lives once at the root; `tsconfig.base.json` is the TypeScript base of
the API and the landing (the app extends Expo's). Decision records:
[ADR 0002](adr/0002-pnpm-monorepo.md), [ADR 0008](adr/0008-public-site-and-app-links.md),
[ADR 0009](adr/0009-postgresql-and-redis-on-the-server.md).

## Runtime topology

```

   ▼
load balancer / WAF              TLS, DDoS protection                  REQUIRES CONFIGURATION
   │
   ▼
web (nginx), one origin          / the landing, /app/* the app's links (open-in-app page),
   │                             /.well-known/ the files that let the phones claim them,
   │                             /api forwarded
   ▼
API (NestJS), N instances        stateless; request ids, redaction, error classification,
   │          │          │        minimum app version
   ▼          ▼          ▼
PostgreSQL   Redis       SMTP server            external services
(required)   (OPTIONAL:  (OPTIONAL: the email   (through the external HTTP client:
             shared rate  outbox delivers        timeouts, retries, correlation)
             limits,      through it)
             cache,
             locks,
             idempotency)
   │
   ▼  (every tier)
Observability: logs (stdout → the platform), error tracking (Sentry, OPTIONAL: one project for
the app, one for the API), traces and metrics (OTLP → collector or provider, OPTIONAL), uptime
checks and alerts (REQUIRES CONFIGURATION)
```

The app talks to the API only, at the base URL built into it (`EXPO_PUBLIC_API_URL`,
[below](#how-the-app-reaches-the-api)). There are no cookies: the access token travels as a bearer
header, the refresh token in the bodies of the session routes, and the app keeps it in the
device's secure storage. Native clients are not subject to CORS, so it stays off (`CORS_ORIGINS`
empty); the Fetch Metadata guard still refuses requests another site makes a browser send (the app
sends neither `Sec-Fetch-Site` nor `Origin` and passes). Several API instances need the shared rate
limit store (`RATE_LIMIT_STORE=redis`, [security.md](security.md#rate-limiting)); everything else
in the API is already stateless.

An installed app is not updated together with the API: contract changes stay additive
([openapi/README.md](../openapi/README.md)), and the API refuses app versions it can no longer serve
([minimum supported app version](#api-appsapi)).

**The reference deployment** of the server side is one Linux server with Docker
([deploy-vps.md](deploy-vps.md)): Caddy terminates TLS for the domain (the load balancer of the
diagram) and forwards everything to the web image, which forwards `/api` to one API instance;
PostgreSQL (or a managed one), its nightly backup and Redis run on an internal network of the same
server. The Deploy workflow publishes the images once per commit, migrates, rolls out and rolls
back by itself ([ci-cd.md](ci-cd.md#deployment)); `infra/terraform/digitalocean` builds the same
server as code. A container platform implements the generic release job of `deploy.yml` instead,
with the same steps.

```
  └─ a box under the logs   every address below, printed each time the API has (re)started
pnpm start, pnpm android or pnpm ios: the app, in another terminal (Metro is interactive)
```

| Service       | Address                                                                 | Moved by                               |
| ------------- | ----------------------------------------------------------------------- | -------------------------------------- |
| Site          | `http://localhost:4331` (the landing, `/api` forwarded to the API)      | `apps/landing/astro.config.mjs`        |
| API           | `http://127.0.0.1:3010/api`; Swagger UI at `/api/docs` (not production) | `PORT` in `apps/api/.env`              |

| Mailpit       | SMTP `localhost:1045`, every message at `http://localhost:8045`         | `MAILPIT_SMTP_PORT`, `MAILPIT_UI_PORT` |
| E2E proxy     | `http://localhost:4010`, in front of the API, for the end-to-end flows  | `E2E_PROXY_PORT`                       |

The ports are the web template's plus 10, so both templates run on one machine at once; the
Compose project name (`template-app`) keeps their containers and volumes apart. Every port is
published on 127.0.0.1 only. A port moved in the root `.env` must be moved in the matching URL of
`apps/api/.env` too; `pnpm dev` points out a mismatch. The first run (`.env` files,
`pnpm db:migrate`, `pnpm db:seed`): [manual](manual.md#5-running-the-api). `pnpm db:up` starts
PostgreSQL alone, `pnpm db:down` stops the services (their data stays in Docker volumes).

The development Redis runs as it would in a deployment: a password, AOF persistence, 256 MB with
`volatile-lru` eviction (only keys with a TTL are evicted), and `apps/api/.env.example` turns on the
shared stores and `REDIS_REQUIRED`. Mailpit keeps messages in memory and accepts mail from anyone
who reaches it, which is why it is never part of a deployment. The integration specs
(`pnpm test:integration`) run on the same services, against their own database (`<db>_test`).

**Production-like stack** (profile `stack`), built from the Dockerfiles:

```
docker compose --profile stack up --build
  migrate   the API image's `migrate` target: checks the applied migrations, then
            prisma migrate deploy, and exits
  api       the `runtime` target: NODE_ENV=production, APP_ENVIRONMENT=stack, TRUST_PROXY=1,
            on the compose PostgreSQL and Redis (REDIS_REQUIRED); not published
  web       the web image: the landing at http://localhost:8090, the app's links and their
            files, and /api forwarded to the API
```

It reads `JWT_ACCESS_SECRET` and the `STACK_*` overrides (another Redis, the in-process stores, the
minimum app versions, Sentry, OpenTelemetry, the app's identity for the link files) from the root
`.env`
([environment.md](environment.md#docker-compose-variables)). Email is off and Swagger UI too
(production). Not a deployment: no TLS, local credentials, nothing published beyond loopback.

**Local OpenTelemetry backend** (profile `observability`, development only):
`docker compose --profile observability up -d` runs a collector, Prometheus, Tempo, Loki and
Grafana in one container: OTLP on 4328 (`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4328` in
`apps/api/.env`, or `STACK_OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-lgtm:4318` for the stack),
Grafana on 3011, Prometheus on 9100 ([observability.md](observability.md#local-backend)).

## How the app reaches the API

The app's HTTP client (`apps/mobile/src/api/`) prefixes every path of the contract (`/api/...`)
with `EXPO_PUBLIC_API_URL`: the API's origin, without `/api` and without a trailing slash.

| The app talks to                                              | `EXPO_PUBLIC_API_URL` in `apps/mobile/.env` | On Android                      |
| ------------------------------------------------------------- | ------------------------------------------- | ------------------------------- |
| the API's dev server (`pnpm dev`, `apps/mobile/.env.example`) | `http://localhost:3010`                     | `adb reverse tcp:3010 tcp:3010` |
| the production-like stack (its web server, `/api` forwarded)  | `http://localhost:8090`                     | `adb reverse tcp:8090 tcp:8090` |
| a deployment (builds): the site's origin, `/api` forwarded    | `https://<your-domain>`, set in EAS         |                                 |

`adb reverse` makes the emulator's or the USB device's `localhost` reach this machine; the iOS
simulator reaches it directly. Plain HTTP is accepted for local hosts only, and production builds
require HTTPS (`apps/mobile/src/config/env.schema.ts`). Values are inlined into the bundle: restart
`pnpm start` after changing them. Deployed values come from the EAS environments
([releases.md](releases.md#environment-variables)).

The API is the app's only backend: there is no mode without it
([adr/0013-real-api-only.md](adr/0013-real-api-only.md)). The e2e build talks to the e2e proxy on
`http://localhost:4010` (`apps/mobile/scripts/e2e-proxy.mjs`), which passes every request to the
API unchanged and fails on demand only what a healthy API never fails, for the Maestro flows
([openapi/README.md](../openapi/README.md#one-implementation-the-api),
[testing.md](testing.md#end-to-end)).

The app's side of the conversation (the session store, renewal, request ids, timeouts, error kinds,
response validation): [mobile-architecture.md](mobile-architecture.md#api),
[Networking](mobile-architecture.md#networking) and
[Authentication](mobile-architecture.md#authentication).

## API (`apps/api`)

```
src/
  main.ts            entry point: crash handlers, telemetry and error tracking, then the server
  server.ts          Nest app: configureApp, Swagger UI outside production, listen
  app.module.ts      modules + global guards: Fetch Metadata, rate limiter (store from
                     RATE_LIMIT_STORE)
  app.setup.ts       HTTP pipeline shared by main, tests and the OpenAPI export
  env/               the validated configuration (the only reader of process.env)
  common/            cross-cutting: error filter (field errors), envelope interceptor, Zod pipe,
                     OpenAPI decorators and named schemas, request id + access log, CSRF guard,
                     rate limit guard, minimum app version and JSON-only middleware, external
                     HTTP client, pagination, types
  observability/     redaction, request context, error tracker (Sentry adapter), telemetry
                     (OpenTelemetry SDK, loaded only when on), application metrics
  infrastructure/    optional infrastructure behind interfaces: redis/ (connection),
                     rate-limit/, cache/, coordination/ (locks, idempotency), mail/ (outbox,
                     worker, SMTP, templates, the `mail` command), push/ (outbox, worker, Expo's
                     push service, templates, the `push` command)
  lifecycle/         shutdown sequence (drain, close, flush)
  auth/              sign-in, refresh rotation with its reuse window, logout, JWT guard, roles
                     guard, @Auth(), password policy, one-time tokens, password recovery, sign-up
  account/           the signed-in user's own account (password, change of email, deletion)
  invitations/       administrators invite people to create an account
  items/             example resource: an owner's items, search, pagination, idempotent create
  devices/           the installations of the app that get push notifications (register, remove)
  users/             me, admin list, owner-or-admin read; the `user:create` command
  health/            liveness and readiness probes
  prisma/            PrismaService (generated client in prisma/generated, ignored by git)
  openapi/           document builder, export script, drift spec
  seed/              development accounts and the member's items (refuses production)
prisma/              schema.prisma, migrations/
scripts/             migrate (development), migrate-deploy (the migration image's command)
test/                integration plumbing
Dockerfile           the API image (`runtime`) and its migration job (`migrate`)
```

**Request pipeline** (`configureApp` and `AppModule`, in order): request id + request context +
access log → helmet headers → `Cache-Control: no-store` → minimum app version (426) → CORS (only
if configured) → JSON-only bodies → global guards: Fetch Metadata (CSRF), then the rate limiter →
route guards (`@Auth`: JWT, then roles) → Zod validation pipe → handler → envelope interceptor; any
exception → error filter (`{ data: null, message, errors? }`,
[error-handling.md](error-handling.md)).

**Module conventions:** one folder per feature (`controller`, `service`, `dto/*.schemas.ts`, specs
next to them, an `*.int.spec.ts`). Controllers are thin: parse (decorators), authorize (`@Auth`),
delegate. Services hold the rules and the queries, including ownership checks
([authorization.md](authorization.md)). DTOs are Zod schemas; their inferred types are the
TypeScript types. Response objects come from explicit `select`s.

**Contract:** the controllers and their Zod schemas are the source of truth. `pnpm contract` runs
the API's `openapi:export` (`openapi/openapi.json`), then the app's `api:types`
(`apps/mobile/src/api/schema.d.ts`). A Zod schema with `.meta({ id: 'Item' })` becomes
`#/components/schemas/Item` (`common/openapi/zod-schema.ts`); one name given to two different
schemas fails the document build. Drift fails `src/openapi/openapi.spec.ts` (`pnpm test`) and the
app's `pnpm typecheck` ([openapi/README.md](../openapi/README.md)).

**Authentication flow** ([ADR 0007](adr/0007-mobile-sessions-with-refresh-tokens-in-the-body.md)):

```
sign-in ─► 200 { accessToken (15 min), refreshToken, expiresIn, user }
          (a new session family: every sign-in, so every device, has its own)
          the app keeps the access token in memory, the refresh token in SecureStore
API call ─► Authorization: Bearer <accessToken>
401 ─► POST /api/auth/refresh { refreshToken } ─► a new pair, the old token used up ─► replay once
answer lost ─► the same token again within 30 s, its successor unused ─► a new pair; the unused
              successor is revoked (superseded): a retry, not a theft
logout ─► POST /api/auth/logout { refreshToken } ─► 204, this device's family ends (idempotent)
any other replay of a used refresh token ─► its whole family ends (theft), logged
password change ─► security version + 1: every access token ends at once; this device carries on
                   with the new session the change answers
```

Refresh tokens are 32 random bytes (43 base64url characters), stored as a SHA-256 hash only. A
session slides 30 days with every renewal, up to 90 days after its sign-in. Concurrent renewals of
one token are serialized by the user's row lock: both answer, the last pair is the live one, and a
family never has two live sessions or none ([security.md](security.md#authentication-and-tokens)).

**Minimum supported app version** (`common/http/app-version.middleware.ts`,
[ADR 0010](adr/0010-minimum-supported-app-version.md)): a request with `X-App-Platform: ios` or
`android` and an `X-App-Version` below `MOBILE_MIN_VERSION_IOS` or `MOBILE_MIN_VERSION_ANDROID`
gets 426 with
`{ data: null, message: "This version of the app is no longer supported: update it to continue" }`
before any other check (authentication, rate limits, validation) and without counting against the
rate limits. Once a minimum is set, a request from the app without a readable version
is refused too. Requests without `X-App-Platform` (curl, probes) and `/api/health/*` pass; an
unset minimum turns the check off. Counted by `app.client.outdated` (`app.platform`). It is a
compatibility gate, not a security control: any client can send any header. The app's part (the
two headers on every request, the update screen) is described in
[releases.md](releases.md#minimum-supported-version); a request that does not send them is never
refused.

**Items, the example resource** (`items/`, behind `@Auth()`): `GET /api/items?limit&offset&q` (the
owner's items, newest first by `createdAt` then `id`; `q` finds titles that contain it, ignoring
case, `%` and `_` taken literally), `POST /api/items` (201), `GET /api/items/{id}` (another user's
item answers 404, like a missing one). An optional `Idempotency-Key` header on the create returns
the first item to a retry with the same body (201 again), answers 422 to the same key with another
body and 409 while the first request is still running
([api-conventions.md](api-conventions.md#idempotency), [below](#locks-and-idempotency)).

**Account deletion** (`account/`, `POST /api/account/deletion { password }` → 204,
[ADR 0012](adr/0012-account-deletion.md)): the password is checked again (403 when wrong, not 401,
which would make the app renew and replay), and the only administrator cannot delete their account
(409). One transaction deletes the user: the database cascades take their items, sessions,
one-time links and queued messages, and an `account_deleted` notice is queued with no user id.
Every access token stops at once (the guard finds no account), every refresh token too (no session
row left). A hard delete, not an anonymization; backups keep the account until they rotate
([security.md](security.md#account-deletion)).

## Optional infrastructure

Every piece below is OPTIONAL: the API runs without it. Each one sits behind an interface with an
in-process implementation, so turning it on is configuration, not a code change, and feature code
never depends on the provider (ESLint keeps `@redis/client`, `@sentry/*` and the OpenTelemetry SDK
out of feature code).

| Capability                | Without configuration (CORE)           | With configuration (OPTIONAL)                      | Switch                                           |
| ------------------------- | -------------------------------------- | -------------------------------------------------- | ------------------------------------------------ |
| Rate limit counters       | in memory, per instance                | Redis, shared by every instance                    | `RATE_LIMIT_STORE=redis`                         |
| Cache                     | in memory, per instance, bounded       | Redis, shared                                      | `CACHE_STORE=redis`                              |
| Locks, idempotency claims | in process                             | Redis, across instances                            | `REDIS_URL`                                      |
| Error tracking            | logs only                              | Sentry                                             | `SENTRY_DSN` (the app: `EXPO_PUBLIC_SENTRY_DSN`) |
| Traces and metrics        | not loaded                             | OpenTelemetry → OTLP                               | `OTEL_EXPORTER_OTLP_ENDPOINT`                    |
| Email                     | off: nothing queued                    | an outbox in PostgreSQL, delivered over SMTP       | `MAIL_SMTP_URL`                                  |
| Job queues                | not included (integration point below) | BullMQ or a managed queue, when a project needs it | code                                             |

Redis is OPTIONAL for the application, not in the template's own setups: development
(`pnpm services:up`, with `apps/api/.env.example`) and the production-like stack run it, with
`RATE_LIMIT_STORE=redis`, `CACHE_STORE=redis` and `REDIS_REQUIRED=true`, as a deployment of more
than one instance needs. Without `REDIS_URL` everything above still runs in process. Decision
record: [ADR 0004](adr/0004-observability-and-optional-infrastructure.md).

### Redis

`infrastructure/redis/redis.service.ts` owns the one connection (node-redis). Only the adapters in
`infrastructure/` use it.

- **Lifecycle:** connects in the background at boot (the boot never waits for Redis), closes on
  shutdown after requests have drained (falls back to destroying the socket after 2 s).
- **Reconnect:** exponential backoff with jitter from 100 ms to 5 s, forever: Redis coming back after
  an outage is picked up without a restart. Only state changes are logged: connected, unavailable
  (once per outage), restored after N seconds; not answering, answering again. An error on a
  connection that is still up (a keep-alive PING answered `BUSY`) is not an outage.
- **Timeouts:** 5 s to connect; each command at most `REDIS_COMMAND_TIMEOUT_MS` (500 ms), already
  sent or not (a Redis that stays connected but stops answering fails the command at the deadline;
  a late reply is dropped). While disconnected, commands fail at once instead of queueing. Replies
  that mean "not now" (`LOADING`, `BUSY`, `READONLY`, `MISCONF` on a full disk, `OOM`...) count as
  unavailable too, and so does `NOPERM` (a key or a command outside the ACL: another
  `REDIS_KEY_PREFIX` than the ACL's, a command it does not list): a configuration fault the
  adapters degrade through, never a 500 on every rate-limited route.
- **Stalls:** after 3 commands in a row get no reply in time, commands fail at once, without being
  sent, for 5 s; then one PING probes Redis: a reply ends the stall, another timeout starts another
  5 s. A Redis that is connected but stalled costs three requests the timeout, not every request.
- **Health:** readiness writes a key of its own under the prefix (`<prefix>health`, 10 s TTL)
  through `EVAL`, as the adapters write (`redis: ok | unavailable | disabled`): a PING would answer
  even where the ACL refuses every key of the API. A Redis that answers but refuses writes (`OOM`
  when full, `MISCONF` when it cannot persist, `READONLY` on a replica, `NOPERM`) is `unavailable`
  too: the adapters cannot work with it. A hard dependency only with `REDIS_REQUIRED=true`, and then
  readiness answers 503 in those states as well, so a deployment or a rollback (both wait for
  readiness) waits until Redis accepts writes again.
- **Keys:** `REDIS_KEY_PREFIX` + feature + key, e.g. `app:cache:profiles:3:user-7`,
  `app:ratelimit:{default:<hash>}:hits`, `app:lock:jobs:report`,
  `app:idempotency:items:create:<hash>`. One prefix per application and environment when they share
  a Redis. Every key the template writes has a TTL (cache generations excepted: a few bytes per
  namespace).
- **ACL for production:** a user limited to `~<prefix>*` and the commands the adapters run:
  `+get +set +del +incr +eval +evalsha +ping +time +pttl +pexpire +zadd +zcard +zrange +zremrangebyscore`
  (plus `+client|setinfo`, `+hello`, `+auth` for the connection handshake). Readiness itself needs
  `+eval` and `+set` on `<prefix>health`.
- **Server:** any Redis-compatible server (Redis, Valkey, managed services). Development
  (`pnpm services:up`) and the production-like stack run `redis:8-alpine`, pinned by digest
  (`docker-compose.yml`); production settings: [security.md](security.md#redis).

### Degradation

What each feature does while an optional Redis is configured but unreachable, or connected but
stalled (it never stops the boot):

| Feature                  | Behavior while Redis is down                                                                                                 | Recovers            |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| Readiness                | 200 `degraded` (503 with `REDIS_REQUIRED=true`), within 2.5 s even when Redis does not answer                                | at once             |
| Rate limiting            | per-instance memory counters: still limits, never fails open                                                                 | at the next request |
| Cache                    | reads miss, writes are skipped: every request is served from the source of truth                                             | at the next request |
| Cache invalidation       | kept and retried before the next cache operation, once per key (past 100 keys, one `invalidate()`); the TTL bounds staleness | when Redis answers  |
| Locks, idempotency       | fail closed: `RedisUnavailableError`, answered 503 in a request                                                              | at the next call    |
| Item creation with a key | the claim is skipped: the database's unique key alone keeps the item single; a concurrent retry waits for the first, no 409  | at the next request |
| Redis stalled            | 3 commands wait the command timeout; then all fail at once for 5 s between PING probes, and the fallbacks above apply        | at the next probe   |
| Everything else          | unaffected                                                                                                                   |                     |

Each fallback is logged once and counted (`app.degraded.operations`); readiness shows it.

Email has its own: while the SMTP server is unreachable or refuses the credentials, messages wait
in the outbox and are retried with backoff (readiness 200 `degraded`, `checks.mail`), and requests
that queue them are not slowed: they only write a row ([Email](#email)).

### Cache

`CacheService` (`infrastructure/cache/`), explicit and opt-in: nothing is cached unless a service
asks, HTTP responses never are.

```ts
const profiles = this.cache.namespace<ProfileView>('profiles', { ttlSec: 60 });
const view = await profiles.getOrSet(userId, () => this.loadProfile(userId));
await profiles.delete(userId); // after changing that profile
await profiles.invalidate(); // after a change that affects every entry
```

- **Use it for** reads that are expensive, frequent, and tolerate being up to `ttlSec` old:
  reference data, computed aggregates, responses of slow external services.
- **Don't use it for** data that changes on every request, data that must be read fresh (balances,
  stock, permissions), or cheap queries (a primary key lookup is already fast).
- **Never cache** tokens, sessions, passwords or hashes, authorization decisions or roles (a
  revoked permission must apply at once), personal data across users (a key must always include
  the owner), or anything a user must see change immediately.
- **Keys:** a namespace per kind of value (`[a-z][a-z0-9-]*`), the key inside it; long keys are
  hashed. **TTL** is mandatory and capped at 24 h. Values are JSON; `undefined` is never cached.
- **Stale data:** delete the entry where the data changes, in the same code path; use `invalidate()`
  (O(1): it bumps the namespace's generation) when a change affects many entries. `getOrSet`
  shares one load between concurrent callers and never stores a result that raced an
  `invalidate()`, or a `set()` or `delete()` of its key on the same instance. The remaining
  window (another instance changing the key while a slow load of it runs) is bounded by the TTL:
  keep TTLs short for data that changes.

### Locks and idempotency

`LockService` and `IdempotencyService` (`infrastructure/coordination/`). The template uses the
claim for one case, item creation with an `Idempotency-Key`; it needs no lock (its scheduled
sweeps are harmless if two instances run them).

- **`withLock(name, ttlMs, work)`:** one instance at a time runs `work` (a scheduled report, a
  migration-like job); the others get `{ acquired: false }` at once. The TTL must exceed the work.
- **`claim(scope, key, { processingTtlSec, doneTtlSec })`:** the first delivery of a message id (a
  webhook event, a job id, an idempotency key) gets the claim for `processingTtlSec`. `complete()`
  it once processed: later deliveries are `done` (acknowledge them) for `doneTtlSec`. `release()`
  it when processing fails, so the sender's retry goes through. A delivery that arrives while
  another one is being processed is `in-progress`: answer it with an error status so the sender
  retries, never with a 2xx, which would lose the message if the first attempt then fails or
  crashes. An attempt that crashes holds the message until `processingTtlSec` runs out, then a retry
  processes it.
- Both are leases with a TTL: an efficiency and deduplication tool, not a correctness guarantee (a
  paused owner can lose its lease). **Payments and anything that must happen exactly once** use the
  database: an idempotency key with a unique constraint, written in the same transaction as the
  effect. Without `REDIS_URL` they hold within one process only.
- **Items** follow that rule: the key and a SHA-256 of the body are stored on the item under a
  unique `(owner_id, idempotency_key)`, which is the guarantee; the claim (scope `items:create`,
  60 s processing, 24 h done) only turns a concurrent retry into a 409 instead of a wait. Without
  `REDIS_URL` the claim holds within one process; while a configured Redis is down it is skipped,
  and the database key alone keeps the item single (the degradation is counted).

### Email

`infrastructure/mail/`, OPTIONAL (`MAIL_SMTP_URL`;
[ADR 0005](adr/0005-transactional-email-outbox.md)). A transactional outbox in PostgreSQL,
delivered over SMTP by a worker inside every API instance:

```
feature transaction ─┬─ the business change (a token, an account...)
                     └─ MailOutboxService.enqueue(tx, { kind, to, userId, payload: ids only })
                                │ a row of mail_messages: kind, address, ids; no body, no secret
                                ▼
MailWorker (every instance) ── claim one due row (lease 2 min, FOR UPDATE SKIP LOCKED)
                             ── render it in a short transaction (a link's token is minted here,
                                only its hash stored) ── SMTP, no transaction open ── record the
                                outcome, fenced by the claim
```

- **Atomic with the change:** the message exists if and only if the transaction that called for it
  committed. After the commit, `notifyQueued()` wakes this instance's worker at once; otherwise
  every worker polls every 5 seconds.
- **Several instances:** one atomic `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED)`
  claims one message for one worker, security notices (the kinds nobody can request) before the
  others, so a flood of requested messages never delays a "your password was changed"; every later
  transition requires the same claim (status `sending`, the same attempt and a claim id of its
  own), so a worker whose lease ran out cannot overwrite another's outcome, and a manual retry,
  which starts the attempts again and clears the claim, never lets two workers record each other's.
  The SMTP timeouts bound each step, not the whole exchange, so a worker renews its lease every
  40 seconds while it sends: a slow relay never makes another worker send the message too.
- **Retries:** the SMTP reply decides: 4xx and connection failures are retried (30 s doubling to
  an hour, equal jitter, at most `MAIL_MAX_ATTEMPTS`), 5xx fails the message at once; refused
  credentials or TLS are retried and reported to the error tracker. Every attempt is counted when
  claimed, so a message that kills its worker runs out of attempts too. A message past its kind's
  validity (`expiresAt`: 30 minutes for a password reset) is dropped unsent, never delivered late.
- **Delivery is at least once:** if the process dies after the SMTP server accepted a message and
  before the outcome is recorded, the lease runs out and another worker sends it again, with the
  same `Message-ID`. SMTP has no exactly-once; links stay single-use whatever the copies: each
  copy is rendered with a token of its own, the earlier copies' tokens keep working, and the first
  one used ends the others ([security.md](security.md#one-time-tokens)).
- **What is stored:** no body and no token, ever: the worker renders the message when it sends it
  and a link's token is minted then (its hash in the database, the token itself only in the
  message in flight). The address is kept while the message may need it (pending, sending,
  failed), then only its keyed hash; CHECK constraints enforce it. Retention: finished rows are
  deleted after 30 days, the address of a failed one is cleared after 7. A deleted account's queued
  messages go with it (cascade); its `account_deleted` notice belongs to no user and is kept until
  sent, then cleared like any other.
- **Limits per address:** the kinds anyone can request (a password reset, a confirmation) are held
  back past one message a minute and `MAIL_DAILY_LIMIT_PER_ADDRESS` a day per address, counted in
  the database, so every instance shares them; an advisory lock on the address serializes
  concurrent requests. Security notices are never held back. The caller answers the same either
  way: what was queued is never told to a client.
- **Links:** `APP_ORIGIN` + `APP_BASE_PATH` (`/app` by default) + the screen, the token in the
  fragment (`https://app.example.com/app/reset-password#token=...`), never a request's `Host`. For
  the app to open them as universal links and App Links, that origin must be its link domain and
  the screens (`reset-password`, `confirm-sign-up`, `confirm-email-change`, `revert-email-change`,
  `accept-invitation`, `forgot-password`, `sign-in`) must be in its link allowlist
  ([mobile-architecture.md](mobile-architecture.md#deep-links)).
- **Without configuration:** nothing is queued (no token is ever minted that cannot be
  delivered), the worker never starts, readiness says `checks.mail: "disabled"`.
- **Operating it:** `pnpm --filter api mail status | test | retry`
  ([manual](manual.md#53-email)); metrics `app.mail.*`
  ([observability.md](observability.md#metrics)). Locally and in CI, Mailpit catches every message.
- **Adding a message:** a kind in the `MailKind` enum (`prisma/schema.prisma`, with its migration),
  a template in `infrastructure/mail/templates/` registered in `templates/registry.ts` (`limited`
  when anyone can cause it, its validity, `compose`), and `MailOutboxService.enqueue(tx, ...)` in
  the transaction of the change it reports, with ids in the payload, never personal data or secrets.

### Push notifications

`devices/` and `infrastructure/push/`, OPTIONAL (`PUSH_ENABLED`, and `EXPO_ACCESS_TOKEN` for
Expo's enhanced security; [ADR 0011](adr/0011-push-notifications-outbox.md)). The email outbox's
design, for Expo's push service, which hands notifications to Apple (APNs) and Google (FCM):

```
app (signed in, notifications allowed) ── PUT /api/devices/{installationId} { pushToken, platform }
                                          devices: one row per installation, one per token
feature transaction ─┬─ the business change (a changed password...)
                     └─ PushOutboxService.enqueue(tx, { kind, userId, payload: ids only })
                                │ a row of push_messages per working device of the account: no text
                                ▼
PushWorker (every instance) ── claim up to 100 due rows (lease 1 min, FOR UPDATE SKIP LOCKED)
                             ── render each (title, body, data.url) ── POST /push/send, no
                                transaction open ── record each ticket, fenced by the claim
                             ── 15 minutes later: claim the sent rows, POST /push/getReceipts ──
                                delivered, failed, or the device disabled (DeviceNotRegistered)
```

- **Devices:** the app registers its Expo push token for the signed-in account under a random id
  of the installation (`PUT`, 204, safe to repeat) at every start and sign-in once notifications
  are allowed, when the user allows them, and when the token changes; at sign-out, before the
  session is revoked, `DELETE` ([mobile-architecture.md](mobile-architecture.md#notifications)).
  One row per installation and one per token: the same installation under another account moves to
  it (a shared phone), and what is still queued for the previous account is dropped unsent (the
  worker compares the device's account with the notification's: `device_moved`); a token
  registered by another installation (a reinstall) leaves its old row.
  Only the caller's own installation can be removed; another account's answers 404, like a missing
  one ([authorization.md](authorization.md)). Registration works with push off too, so turning it on
  later reaches every phone that registered.
- **Atomic with the change:** the notifications exist if and only if the transaction that called
  for them committed, one per device of the account whose token works at that moment. After the
  commit, `notifyQueued()` wakes this instance's worker at once; otherwise every worker polls every
  5 seconds.
- **Several instances:** one atomic `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)`
  claims a batch (Expo takes at most 100 per request) for one worker; every later transition
  requires the same claim (a send: status `sending` and the attempt; a receipt: status `sent` and
  its ticket), so a worker whose lease ran out cannot overwrite another's outcome.
- **Retries:** a request that fails (timeout, network, 429, 5xx) leaves the whole batch for a retry
  (30 s doubling to an hour, equal jitter, at most 5 attempts); the HTTP client never retries a
  send by itself, which could notify twice. Per notification, its ticket or receipt decides:
  `MessageRateExceeded` is retried, `DeviceNotRegistered` disables the device (nothing more goes to
  it until the app registers again; outcome `unregistered`), any other error fails it, and refused
  credentials (`InvalidCredentials`, `MismatchSenderId`) also reach the error tracker. A
  notification past its kind's validity (a day for `password_changed`) is dropped unsent; a receipt
  still missing a day after the send never comes (`no_receipt`).
- **Delivery is at least once:** if the process dies after Expo accepted a batch and before the
  tickets are recorded, the lease runs out and another worker sends it again.
- **What is stored:** a device's token, platform, app version (its `X-App-Version`, when valid) and
  last registration; a notification's kind, account, device, ids, status and the category of its
  last failure, never the service's text. The text is rendered when it is sent and stored nowhere.
  CHECK constraints keep the states consistent. Retention, by an hourly sweep: finished rows after
  30 days, a device whose token died 30 days after, one not registered for 270 days (when Firebase
  treats a token as stale). A deleted account's devices and notifications go with it (cascade).
- **What a notification carries:** a title, a body and `data.url`, an internal path the app opens
  only through its link allowlist; sound, high priority and the Android channel `default`. The text
  passes through Expo, Apple and Google and shows on lock screens: never personal data. Tokens are
  device identifiers: never logged (a device is named by its id).
- **Security:** without `EXPO_ACCESS_TOKEN` (with push security turned on in the Expo account),
  anyone who learns a device's push token can send to it through Expo
  ([security.md](security.md#push-notifications)).
- **Without configuration:** nothing is queued, the worker never starts, readiness says
  `checks.push: "disabled"`.
- **Operating it:** `pnpm --filter api push status` ([manual](manual.md#59-push-notifications));
  metrics `app.push.*` and alerts `ApiPushBacklog`, `ApiPushDeliveryFailed`
  ([observability.md](observability.md#metrics),
  [incident-response.md](incident-response.md#19-push-notifications-not-delivered)). The
  integration suite runs the worker against a fake push service.
- **Adding a notification:** a kind in the `PushKind` enum (`prisma/schema.prisma`, with its
  migration), a template in `infrastructure/push/push.templates.ts` (its validity, `render`: the
  title, the body and a `data.url` the app's `links.ts` accepts), and
  `PushOutboxService.enqueue(tx, ...)` in the transaction of the change it reports, then
  `notifyQueued()` after the commit ([how-to.md](how-to.md#send-a-push-notification)).

### Account credentials

Password recovery and change ([security.md](security.md#password-recovery)):

```
auth/password-policy.ts      the rules of a new password (length, common list, predictable, account)
auth/password.ts             Argon2id hash and check, NFKC-normalized
auth/account-tokens.ts       one-time tokens: mint (hash stored), consume (locked, once), sweep
auth/password-reset.service  POST /api/auth/password-resets (+ /confirm); answers before the lookup
auth/sign-up.service         POST /api/auth/sign-ups (+ /confirm), when SIGN_UP_ENABLED; sign_ups table
account/                     the signed-in user's own account: POST /api/account/password, /email
                             and /deletion; the change-of-email links: /api/auth/email-changes/*
templates/password-*.ts      the reset link (token minted at send time) and the changed notice
templates/sign-up-*.ts       the confirmation link, and the notice to an address that has an account
templates/email-change*.ts   the link to the new address, the notice to an address that has an account
templates/email-changed.template.ts  the notice to the previous address, with the undo link (7 days)
templates/account-deleted.template.ts  the notice that the account was deleted (no link)
invitations/                 administrators invite (/api/admin/invitations), people accept
                             (/api/auth/invitations/accept); the invitations table
templates/invitation.template.ts     the invitation link (7 days)
```

- **`users.security_version`** ([ADR 0006](adr/0006-security-version-in-access-tokens.md)):
  incremented by every credential change, in the same transaction; access tokens carry it (`sv`)
  and `JwtAuthGuard` compares it on every request, so the change ends them at once. One-time tokens
  record it too: a token minted before a change no longer works.
- **Sessions after a change:** a password reset ends every session and signs nobody in; a change of
  password while signed in ends every session too and answers the device that made it a new one
  (`Session`, like a sign-in); accepting an invitation and confirming a sign-up also answer a
  session.
- **Lock order:** the account's row (`lockUser`), then the token's row: the same order as every
  session change, so a reset, a change, a deletion, a sign-in and a refresh never deadlock or
  interleave.
- **Sign-up without half-made accounts:** a sign-up lives in `sign_ups` until its link is
  confirmed (with the password chosen); only then is the `users` row created, in the transaction
  that deletes the sign-up. Nothing else in the API ever sees an unconfirmed address.
- **Email off:** `GET /api/auth/capabilities` answers
  `{ passwordReset: false, signUp: false, emailChange: false, invitations: false }`, so a client
  can hide what needs email; the reset, change-of-email and invitation routes answer 503 (sign-up
  cannot be on without email: the boot refuses it). Changing the password and deleting the
  account work either way (the notice is then not sent).

### Job queues

Not included: no queue library is installed until a project needs one. The integration point, when
work must leave the request (image processing, document generation, heavy computations; email
and push notifications have their own outboxes, above):

```
API ──enqueue (job name, payload with ids only)──► queue (Redis: BullMQ, or SQS / Pub/Sub / ...)
                                                       │
                                     worker (apps/worker) ◄┘  same env validation, logger,
                                                              redaction, error tracking,
                                                              telemetry and shutdown sequence
```

- Add `apps/worker` as another app (see [Extending](#extending)): its own entry point importing the
  same `observability/` setup and the modules it needs, no HTTP server, SIGTERM stops taking jobs
  and finishes the current one.
- Producer side: a `JobQueue` interface in `infrastructure/` with the provider adapter, so feature
  code enqueues without knowing the provider; payloads carry ids, never personal data or secrets.
- Jobs are idempotent (they will be retried): check and claim with `IdempotencyService`, or make the
  write itself idempotent. Propagate the request id (and trace context) in the job's metadata.
- With BullMQ on the same Redis, its keys have no TTL: keep `maxmemory-policy` on `volatile-*` or
  `noeviction` (the template's `volatile-lru` already protects them), or give queues their own
  Redis.

## Public site and app links (`apps/landing`)

The landing is static pages built by Astro and styled with Tailwind CSS, in English at `/` and
Spanish at `/es/` with typed dictionaries (`src/i18n`): the home page, privacy, account deletion
(the URL Google Play's Data safety form asks for), the open-in-app page and the not-found page.
Nothing runs per request and nothing ships to the browser but HTML and CSS: a 0 kB JavaScript
budget (`performance-budget.json`, `pnpm perf:check`) and a CSP with `script-src 'none'` keep it
so. What to change for a product (the name, the privacy address, the store pages, the share
picture): [manual](manual.md#57-the-landing).

The web image (`apps/landing/Dockerfile`, nginx-unprivileged) serves it on one origin with
everything else that is public:

| Path                                                                      | Answer                                                                                                                    |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `/`, `/es/`, `/privacy/`…                                                 | the landing; its absolute links written with `APP_ORIGIN` as they are served (the image is built once, for a placeholder) |
| `/app/*`                                                                  | the app's links: the phone opens them in the app; anywhere else, the open-in-app page, at that address, with no redirect  |
| `/.well-known/apple-app-site-association`, `/.well-known/assetlinks.json` | JSON written at start from the app's identity, claiming `/app/*`; 404 without it                                          |
| `/api/*`                                                                  | the API (`API_UPSTREAM`), with the client's address in `X-Forwarded-For` and the probes kept private                      |
| `/healthz`                                                                | the web server's own health                                                                                               |

The links the API emails (`APP_ORIGIN + APP_BASE_PATH + /<screen>#token=…`), the paths the app
accepts (`apps/mobile/src/lib/links.ts`) and the paths the link files claim are the same `/app/*`:
`scripts/web-server-routes.test.mjs`, `scripts/app-links.test.mjs` and the landing's
`src/lib/links.spec.ts` fail when one of them changes alone. The token of an emailed link travels in
the fragment, which neither nginx nor the API ever receives. The variables:
[environment.md](environment.md#web-variables); the checks after a deployment: `pnpm smoke`
([testing.md](testing.md#smoke-test)).

## Key decisions

| Decision                                                                      | Why                                                                                       |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| pnpm workspace, one lockfile                                                  | One install, one audit, one set of hooks and gates for every app.                         |
| Contract generated from Zod + controllers, committed and drift-checked        | Validation and documentation cannot disagree; the app's types follow; changes are a diff. |
| Tokens in the body, no cookies                                                | A native client has no cookie jar to protect: no CSRF on the session, CORS stays off.     |
| Access token in memory, refresh token in secure storage + rotation            | No token in plain storage; stolen refresh tokens are detected on reuse.                   |
| A 30 s reuse window on renewal                                                | A phone that lost an answer and retries is not signed out as a thief.                     |
| Minimum app version enforced by the API                                       | Stores cannot force updates; the API stops versions it can no longer serve.               |
| Validated env, fail fast                                                      | Misconfiguration stops the deploy instead of failing a request later.                     |
| ESLint `strictTypeChecked` + TypeScript `strict` + `noUncheckedIndexedAccess` | Bugs found by the compiler and linter, not by users.                                      |
| Integration tests on a real PostgreSQL                                        | Locks, constraints and migrations are part of the behavior.                               |

Record new decisions as ADRs in `docs/adr/`.

## Extending

- **New API module:** copy `items/` (an owner-scoped resource with search, pagination and an
  idempotent create), following the module conventions above. The Nest CLI generators produce
  class-validator DTOs and Jest specs, which this template does not use.
- **New database table:** edit `apps/api/prisma/schema.prisma`, then `pnpm db:migrate` creates,
  applies and regenerates ([database.md](database.md#migrations)).
- **Contract change:** in the API first, then `pnpm contract`, commit both generated files
  ([openapi/README.md](../openapi/README.md#workflow)).
- **New screen:** [the recipe](mobile-architecture.md#adding-a-feature): API hooks in
  `apps/mobile/src/features/<feature>/api.ts`, the screen, a thin route, tests.
- **Another app** (background worker, admin console): a new folder in `apps/` with its own
  `package.json` (picked up by the workspace), a tsconfig extending `tsconfig.base.json` for a
  Node.js app, `test`/`typecheck`/`build` scripts (picked up by the root commands), a block in
  `eslint.config.mjs`, and its own Dockerfile if it runs as a container. A background worker
  (OPCIONAL) follows the API's patterns: validated env, structured logs, graceful shutdown on
  SIGTERM, idempotent jobs.
- **Optional infrastructure** (queues, object storage, search, push delivery): add it like the
  existing adapters: an interface and an in-process or fake implementation in `infrastructure/`,
  the provider adapter next to it, its variables in the env schema, its health in the readiness
  probe (hard or degradable), its degraded behavior in the table above, and an integration spec
  that runs in CI against a throwaway container.
