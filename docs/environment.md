# Environment variables and secrets

## Rules

- The API validates its configuration once, at boot (`apps/api/src/env/env.schema.ts`). A missing
  or malformed value stops the process and names the variable; values are never printed. The app
  validates its own public configuration when the app config is evaluated and again at startup
  ([below](#app-variables)).
- API code imports `env` from `apps/api/src/env/env.ts`; reading `process.env` elsewhere is a lint
  error (the app's equivalent: `apps/mobile/src/config/env.ts`). A new API variable goes into the
  schema, `apps/api/.env.example`, its unit spec (`apps/api/src/env/env.schema.spec.ts`) and the
  table below, in the same pull request.
- `.env` files hold local development values only and are never committed (`.gitignore`, the
  pre-commit hook and the secret scans enforce it). Only `.env.example` files are committed.
- Variables already set in the environment win over `.env` (containers and CI set them directly).
  The API's tests never load `apps/api/.env` (`NODE_ENV=test`): their configurations set fixed
  values, and the integration specs take only the servers' addresses from the file.

| File                        | Read by                                                                                                                                        | Committed |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------- |

| `apps/api/.env.example`     | documentation of every API variable                                                                                                            | yes       |
| `.env` (root)               | `docker compose` (ports, `REDIS_PASSWORD`, the production-like stack's secret and settings) and `pnpm dev`'s banner                            | no        |

A secret.                                                                                                                                                                                                                                                                                            |

A configuration error stops the boot and names the variable: a missing required value, a malformed
one, or an optional feature asked for without what it needs (`RATE_LIMIT_STORE=redis`,
`CACHE_STORE=redis` or `REDIS_REQUIRED=true` without `REDIS_URL`; `MAIL_SMTP_URL` without
`MAIL_FROM` or `APP_ORIGIN`; `SIGN_UP_ENABLED=true` without `MAIL_SMTP_URL`). An optional
integration that is simply not configured never stops anything.

An empty value reads as unset (convenient in `.env` files and compose), except for the variables
that only take listed values or a name: `LOG_LEVEL`, `LOG_FORMAT`, `RATE_LIMIT_STORE`,
`CACHE_STORE`, `REDIS_REQUIRED`, `SIGN_UP_ENABLED`, `REDIS_KEY_PREFIX` and `OTEL_SERVICE_NAME`
refuse an empty value; leave them out instead. The flags take `true` or `false`, nothing else: a
typo never silently means `false`.

The stack's API has fixed values besides: `NODE_ENV=production`, the compose database,
`TRUST_PROXY=1` (one proxy hop: the web container, which replaces `X-Forwarded-For`),

## Web variables

The web image (`apps/landing/Dockerfile`, [ADR 0008](adr/0008-public-site-and-app-links.md)): the
landing, the app's links and the files that let the phones claim them, and `/api` forwarded to
the API. Its settings are runtime environment variables, checked by
`apps/landing/nginx/18-validate-runtime-config.sh` before nginx starts: a missing or malformed value
stops the container and names the variable, never its value
(`scripts/validate-runtime-config.test.mjs`).

| Variable                                              | Default           | Purpose                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `APP_ORIGIN`                                          | none: required    | The site's public origin (`https://app.example.com`: no path, no trailing slash), written into the landing's absolute links (canonical and alternate links, the share picture, the sitemap, `robots.txt`) as they are served. The same origin as the API's `APP_ORIGIN`, the domain of the links its emails carry.                                                              |
| `API_UPSTREAM`                                        | `http://api:3000` | Where `/api` goes: an origin, `http(s)://host[:port]`, with no path and no trailing slash (nginx would send every call to that path instead of its own); anything else stops the container. Its host is looked up through DNS every 10 seconds (a redeployed API gets a new address), so it must be a DNS name: one only in `/etc/hosts` (`docker run --add-host`) is not seen. |
| `APPLE_TEAM_ID`, `IOS_BUNDLE_ID`                      | unset             | Together: the Team ID of the Apple Developer account (10 characters) and the app's bundle identifier (`com.example.templateapp`; the production variant's, `apps/mobile/app.config.ts`). They write `/.well-known/apple-app-site-association`, claiming `/app/*`; unset, it answers 404 and iPhones open the links in the browser.                                              |
| `ANDROID_PACKAGE`, `ANDROID_SHA256_CERT_FINGERPRINTS` | unset             | Together: the app's application id and the SHA-256 fingerprints of the certificates that sign it (`AB:CD:…`, capitals, comma-separated: Play App Signing's key, and the upload key for builds installed outside Play). They write `/.well-known/assetlinks.json`; unset, it answers 404 and Android opens the links in the browser.                                             |
| `APP_RELEASE`                                         | from the build    | The build the image holds (CI passes the commit SHA), for `docker inspect`, the deployment's records and `/release.json` (`pnpm smoke --release`). Letters, digits, `.`, `_`, `+` and `-`; never set it by hand in a deployment.                                                                                                                                                |

The link files are written at start (`apps/landing/nginx/19-app-links.sh`, into `/tmp`, so a
read-only root filesystem works), served as JSON without a redirect and cached for 5 minutes;
`pnpm smoke --require-app-links` checks them on a deployment. The domain the app claims
(`APP.linkDomain` in `apps/mobile/app.config.ts`) must be this origin's host
([mobile-architecture.md](mobile-architecture.md#deep-links)).

## App variables

The app's configuration holds no secret and nothing of the API's. Its variables are public:
`EXPO_PUBLIC_*` values are inlined into the JavaScript bundle at build time and readable by anyone
who has the app. They are validated by `apps/mobile/src/config/env.schema.ts` when the app config
is evaluated (a bad value fails the build) and again at startup. Locally they come from
`apps/mobile/.env`; builds get them from `apps/mobile/eas.json` and the EAS environment variables.

The one that ties the app to the API is `EXPO_PUBLIC_API_URL`: the API's base URL, without `/api`
and without a trailing slash. HTTPS, except plain HTTP for `localhost`, `127.0.0.1`, `10.0.2.2`
and `[::1]` outside production. `apps/mobile/.env.example` points it at `pnpm dev`'s API
(`http://localhost:3010`, with `adb reverse tcp:3010 tcp:3010` on Android); the mock API is
`http://localhost:4010` ([architecture.md](architecture.md#how-the-app-reaches-the-api)).
The others are `EXPO_PUBLIC_APP_ENV` (set per build profile), `EXPO_PUBLIC_SENTRY_DSN` and
`EXPO_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` (the app's own Sentry project) and `EXPO_PUBLIC_FLAGS`
(feature flag overrides, refused in production), and `EXPO_PUBLIC_STORE_URL_IOS` and
`EXPO_PUBLIC_STORE_URL_ANDROID` (the store pages the update screen opens). The full table, the
build-time variables
(`APP_VARIANT`, `SENTRY_*`, `GOOGLE_SERVICES_JSON`) and where each value lives:
[releases.md](releases.md#environment-variables).

## Local, staging and production

- **Local:** `cp apps/api/.env.example apps/api/.env`, fill `JWT_ACCESS_SECRET`; `pnpm services:up`
  (or `pnpm dev`) starts PostgreSQL, Redis and Mailpit from `docker-compose.yml`. The ports are the
  web template's plus 10, so both templates run on one machine
  ([ADR 0002](adr/0002-pnpm-monorepo.md)). The database listens on 5452, not 5432 (nor the web
  template's 5442), so it does not collide with a PostgreSQL installed on the machine. If 5452 is
  taken, set `DB_PORT` in a root `.env` and the same port in `DATABASE_URL`. Redis listens on 6399,
  not 6379, with the password `app`: `REDIS_PORT` and `REDIS_PASSWORD` in the root `.env` and the
  same in `REDIS_URL` to change them. Email goes to Mailpit, SMTP on 1045 and its web UI on 8045,
  not Mailpit's usual 1025 and 8025: `MAILPIT_SMTP_PORT`, `MAILPIT_UI_PORT` in the root `.env` and
  the port in `MAIL_SMTP_URL` to move them. The API listens on 3010 (`PORT`). The app:
  `cp apps/mobile/.env.example apps/mobile/.env` ([manual](manual.md#5-running-the-api)).
- **Production-like stack:** `cp .env.example .env`, fill `JWT_ACCESS_SECRET`, then
  `docker compose --profile stack up --build`
  ([architecture.md](architecture.md#local-development)).
- **Staging and production** are separate infrastructure: separate databases, separate secrets,
  never shared. Staging mirrors production settings (`NODE_ENV=production`,
  `APP_ENVIRONMENT=staging`) with its own data, never a copy of production personal data. The
  repository has no deployment of the API: where it runs, and how its variables get there, is
  REQUIERE CONFIGURACIÓN per provider. The app's preview builds point at the staging API and its
  production builds at the production one (`EXPO_PUBLIC_API_URL` per EAS environment).

## Secrets

- The API's production and staging values live in the deployment platform's secret manager;
  REQUIERE CONFIGURACIÓN per provider. The app's build secrets (`SENTRY_AUTH_TOKEN`,
  `GOOGLE_SERVICES_JSON`) are EAS environment variables of visibility secret, and the release
  workflows' `EXPO_TOKEN` lives in the GitHub environments `preview` and `production`
  ([releases.md](releases.md#environment-variables), [ci-cd.md](ci-cd.md#secrets-and-variables)).
- Least privilege: the API gets only what it reads; the migration job gets only `DATABASE_URL` (as
  the production-like stack's `migrate` service does).
- Nothing in the app is secret: an `EXPO_PUBLIC_*` value, or anything else in the bundle, is
  readable by anyone who has the app. A key the app needs is a public one, restricted on the
  provider's side.
- Rotation: generate, deploy, verify, then revoke the old value. `JWT_ACCESS_SECRET` has its own
  procedure, with or without a grace period ([security.md](security.md#secret-rotation)); it never
  signs anyone out, since refresh sessions do not depend on it: an access token the new secret
  refuses is renewed by the app with its refresh token.
- A secret that reached git, a log or a ticket is compromised: rotate it.
